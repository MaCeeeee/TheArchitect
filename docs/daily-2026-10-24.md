# 2026-10-24 — Eine PHP-Warnung, die nichts betraf, und ein Korpus, der seit sieben Tagen tot war

## Die Geschichte in drei Sätzen

Anlass war eine Hostinger-Mail zu PHP-Lücken — auf keinem der Server läuft PHP, die Warnung war
gegenstandslos. Beim Nachsehen kam ein echter Ausfall zum Vorschein: Der Rechts-Korpus auf
Server B war für die App **seit dem 17.10.** nicht erreichbar, und zwar aus drei gleichzeitigen
Gründen — abgelaufene Tailscale-Schlüssel auf allen drei Geräten, eine Bridge auf Server B, die
nach einem Neustart ohne Netz hing, und ein veralteter DNS-Eintrag. Nach gut zwanzig Minuten lief
alles wieder; der Schlüsselablauf ist jetzt abgeschaltet, zwei tote Subdomains sind gelöscht.

---

## 🆕 Feature & Fähigkeit

1. **Der Rechts-Korpus ist für die App wieder erreichbar.** Kein `[corpus] connection error`
   mehr im App-Log nach dem Neustart, Server meldet „Server running".
2. **Das Tailnet läuft nicht mehr nach 180 Tagen aus.** Für alle drei Geräte (App-VPS, Server B,
   Mac) steht in der Admin-Konsole „Expiry disabled".
3. **Der App-VPS ist auf Stand.** 58 Pakete eingespielt, darunter das eine offene
   Sicherheitsupdate; kein Neustart nötig.
4. **Zwei Altlasten im DNS sind weg.** `n8n.just4.io` und `nocodb.just4.io` zeigten auf einen
   Server, auf dem weder n8n noch NocoDB läuft. Die gültigen Adressen sind
   `n8n.thearchitect.site` und `waitlist.thearchitect.site`; die globale CLAUDE.md nennt jetzt
   die richtige n8n-Adresse.

---

## 📌 Learnings heute

1. **„Up" ist kein Beweis für „erreichbar".** Ein Container ohne Netz zeigt denselben Status wie
   einer mit. Geprüft wird der Lauscher (`ss -ltnp`), nicht die Statusspalte.
2. **Gleichzeitige Abmeldung mehrerer Geräte hat eine gemeinsame Ursache.** Zwei, dann drei
   Geräte „Logged out" — das ist der 180-Tage-Ablauf, kein Einzelfehler.
3. **Timeout und „refused" sind verschiedene Diagnosen.** Das eine heißt „kein Weg", das andere
   „Weg da, niemand zu Hause". Die Unterscheidung hat die Suche auf Server B gelenkt.
4. **Ein Ausfall ohne Alarm dauert eine Woche.** Der Korpus war sieben Tage tot, gefunden hat
   ihn eine PHP-Warnung, die nichts damit zu tun hatte.

---

## Die Warnung, die keine war

Geprüft an drei Stellen: keine Compose-Datei, kein Dockerfile, kein Container mit PHP; kein
`x-powered-by`-Hinweis an den öffentlichen Adressen; auf dem VPS selbst kein `php`, kein Paket,
kein Container. Der Beifang beim Login war wichtiger: ein offenes Sicherheitsupdate und
56 normale.

Das Update hatte eine Nebenwirkung: Docker wurde mit aktualisiert (29.4.3 → 29.9.2), der Dienst
startete neu und mit ihm alle Container. Kurz lieferte `thearchitect.site` **502**. Die App war
schneller oben als Neo4j, stürzte viermal mit `ECONNREFUSED` ab und stand beim fünften Versuch.
Der bekannte Neo4j-Race — diesmal hat er sich nach etwa 30 Sekunden selbst erledigt.

---

## Drei Ursachen für einen Ausfall

Der Korpus-Fehler stand schon vor dem Update im Log. Die Diagnose lief in Schichten, und jede
Schicht hatte ihre eigene Ursache:

| Schicht | Befund | Reparatur |
|---|---|---|
| Tailnet, App-VPS | `tailscale status` → „Logged out" | `tailscale up --hostname=primary` (Flag Pflicht) |
| Tailnet, Server B | `tailscale ping` → „peer's node key has expired" | `tailscale up --hostname=data-server` |
| Port auf Server B | „Connection refused" statt Timeout | Bridge neu anlegen |
| DNS | `n8n.just4.io` zeigt auf den falschen Server | Eintrag gelöscht |

Der lehrreiche Teil ist die dritte Zeile. Die Korpus-Datenbank auf Server B lief seit sieben
Tagen gesund. Ausgefallen war nur der kleine Weiterleiter, der ihren Port ins Tailnet hält —
`Exited (143) 7 days ago`, also beim Neustart des Servers am 17.10. Nach `docker start` zeigte er
„Up", lauschte aber trotzdem nirgends: `docker inspect` meldete **leere Netze**, `ss` keinen
Lauscher. Beim Neustart hatte es die Tailnet-Adresse nicht gegeben, an die er binden sollte. Erst
löschen und mit identischer Konfiguration neu anlegen half.

Auch die Reihenfolge der Befunde war eine Lektion: Der erste Timeout vom Mac aus sagte **nichts**
über Server B — der Mac selbst war abgemeldet. Erst der Test vom App-VPS trennte die Ursachen:
Timeout heißt Tailnet weg, „refused" heißt Port auf Server B.

---

## Offen am Tagesende

- **Restrisiko Reboot:** Startet Server B neu und ist Tailscale langsamer als Docker, hängt die
  Bridge wieder ohne Netz. Robuster wäre ein Lauscher auf allen Adressen plus Firewall-Regel —
  nicht umgesetzt. Diagnose und Befehle stehen im Memory (`reference_tailnet_bridge_outage`).
- **Kein Monitoring auf den Korpus-Zugriff** — der Ausfall wäre sonst weiter unbemerkt geblieben.
